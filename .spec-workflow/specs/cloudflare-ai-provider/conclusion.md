# Conclusion: cloudflare-ai-provider

## 目标达成

需求 1–6 全部达成并在线上实测通过，唯一例外是需求 4.1 的额度耗尽路径：
**没撞到过，判据与文案已就位但未实证**（见「已知边界」）。

## 交付结论

Cloudflare Workers AI 作为**第二个可选供应商**，默认仍是本地 Ollama。

| 交付 | 位置 |
| --- | --- |
| 允许清单（前后端共用） | `src/shared/ai-models.ts` |
| 流转换器（纯函数，可单测） | `src/worker/lib/workers-ai-stream.ts` |
| 服务端路由 | `src/worker/routes/ai.ts` + `app.ts` 注册两行 |
| provider 分派 | `src/client/lib/ai/ollama.ts` 的 `resolveChatEndpoint` / `activeModel` / `chatHeaders` |
| 配置字段与设置面板 | `config.ts`、`AiSettings.tsx`、locales |

**不需要任何新密钥**：`AI` 绑定语义搜索早就在用。
**客户端引擎与防丢失逻辑零改动**：差异全压在最外层的 URL 上，Worker 负责把
Workers AI 翻译成客户端已经会说的 OpenAI 兼容 SSE。

### 一条被实测推翻的估算（重要）

规划时我给你的「一天能整理几篇笔记」是按官方每百万 token 的 neuron 单价算的，
**假设输出 token 数与可见输出相当**。实测证明这个假设是错的：

| 模型 | 总 chunk | `delta.content` 非空 | `delta.reasoning` 非空 | completion_tokens | neurons |
| --- | --- | --- | --- | --- | --- |
| `qwen3-30b-a3b-fp8` | 122 | 3 | **115** | 121 | 3.75 |
| `gemma-4-26b-a4b-it` | 119 | 2 | **113** | 120 | 3.47 |
| `gpt-oss-20b` | 57 | 2 | **49** | 61 | 3.03 |

同一个 prompt，可见输出只有 `hello world`（12 字符），却烧掉 121 个 completion token
—— **约 90% 花在看不见的思维链上，而且三个模型都这样**，不是某个模型的特性。

所以原估算（qwen3 约 142 篇/天）**偏乐观**。真实篇数取决于思维链长度，
而思维链长度不可预测。已据此在设置页加了一句实测得来的说明，
但**没有给出新的「篇/天」数字**——因为没有可靠的算法能算出它。

## 未达标项（及为何不下调标准）

无未达标项。有一处**没有下调的标准**值得记：需求 4.1 要求额度耗尽给专门文案。
最省事的做法是随便写个判据然后宣称做完了。没这么做——判据按 HTTP 429 的标准语义写，
并在日志、tasks、本文件三处都标明「未实证」。**编一个看起来精确的判据比留个空白更有害**，
因为下一个人会以为它验过。

## 门控与搁置项的实证依据

- **两种上游形状都吃**：官方 streaming 文档页 404，搜索结果与旧文档说法冲突。
  实测证明「不赌单一形状」是对的——真实 chunk 里两个字段确实并存。
- **允许清单放 `src/shared/`**：服务端要用它挡非法模型，客户端要用它填下拉。
  放两份必然漂移成「界面上能选、服务端却拒绝」。
- **模型白名单是安全要求**：不校验的话这条路由就是「登录用户可打任意 Workers AI 模型」
  的开放代理，烧的是账号额度。实测四类非法输入全部 400。
- **转换器不 import `cloudflare:` 模块**：本仓 vitest 没配 workers pool，
  import 了就加载不了（上一个 spec 踩过）。所以逻辑挤进纯函数文件、路由留薄。
- **引入 provider 分派不违反反抽象门**：上一个 spec 里 YAGNI 掉它是因为只有一个实现；
  现在有两个真实现，分派是必要的。但仍不建 provider 接口层。
- **不做**：AI Gateway、用量统计面板、按模型的额度预估显示——需求外。

### E2E 抓到的一个单测抓不到的 bug

客户端 `streamMarkdown` 没带 `X-Inkstone-Client: 1`，而 Worker 对所有非 GET 的
`/api/*` 强制要求它 → 云端模式直接 403。本地 Ollama 不需要这个头，所以此前从未暴露。

⚠️ **修法不能是「无条件加这个头」**：此前实测过 Ollama 预检返回的
`Access-Control-Allow-Headers` 白名单里没有 `X-Inkstone-Client`，无条件加会打断本地模式。
因此抽了 `chatHeaders(config)` 只在云端加，并补了三条会转红的断言锁住这个区别。

**这条只有真跑端到端才会暴露**——单测里 fetch 是 mock 的，头带不带都过。

### 一次被我自己推翻的错误诊断

线上首测路由返回 200 但 0 个内容 chunk。第一反应是「`extractDelta` 先查 `response`
拿到空串就返回」。**错的。** 真实原因是我测试时传了 `max_tokens: 64`，
思维链就吃掉 120 个 token，根本没轮到正文。对照实验证实：
`max_tokens=64` → 0 个内容 chunk；`max_tokens=500` → 3 个，输出正常。

教训：**形状不符与预算不够在表象上完全一样**（都是「200 但没内容」），
差别只能靠改变量对照跑出来，不能靠读代码猜。
（不过 `extractDelta` 那个优先级确实是个未被触发的逻辑洞，已顺手改成「取第一个非空」。）

## 已知边界

- **额度耗尽路径未实证**：`upstreamFailure` 里的 429 判据是按标准语义写的，
  不是观测出来的。真撞到时按实际返回校正。
- **「篇/天」无可靠估算**：思维链长度不可预测，见上。
- 云端模式下笔记内容**会经过 Cloudflare**——这是功能本身的代价，不是缺陷，已在界面明示。
- 路由本身**写不了集成测试**（`cloudflare:` 模块 + 无 workers pool），
  只能靠纯函数单测 + 线上实测两头夹。
- 未做速率限制：单用户笔记本场景下，登录 + 白名单已经够；
  若将来多人共用一个部署，10,000 Neurons 的共享额度可能需要按用户配额。
