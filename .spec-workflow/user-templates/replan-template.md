# REPLAN — {{PROJECT_NAME}}

> **朝前看的复盘**：每个 spec 收尾时追加一节——发现了什么、计划怎么变、下一步做什么。
> 朝后看的验收在各 spec 自己的 `conclusion.md`。两者别混着写。
>
> 这份文件是**可选的**。项目不维护它就不必创建——`closureFrom` 未配置时也不会有人催。

## 唯一的机器判据

**`## ` 标题里包含 spec 名，就算这个 spec 记过了。** 就这一条。

```markdown
## my-spec-name
```

上面这行已经足够让 `spec-status` / `specloop closure` 不再报「欠复盘」。
下面全是**约定**，不影响判定——但其中两处能换来实际功能。

## 两处约定能换来功能

**① 标题里的 `R#` 会被解析出来**（dashboard 用它标轮次）。认两种写法：

```markdown
## R47 write-surface-parity — 后端放开了，界面还灰着          ← 行首式
## write-surface-parity（R47，2026-07-28）——后端放开了…       ← 后缀式
```

后缀式**要求括号后紧跟逗号**：`（R47，` 或 `(R47,` 都行，
而 `（R47）` 少了逗号，**取不到**。

**② 写成 `- [ ]` 的行才是 dashboard 能勾的待办**，勾了会写回文件。
纯陈述（新发现、经验教训）用普通 `-` 条目，别写成待办——
不打算勾的复选框会把这个视图变成噪音。

## 推荐结构

一节对应一个 spec。下面的子标题都是可选的，按这一轮实际有什么写什么，
**没有的整段删掉，别写「无」**。

```markdown
## <spec-name>（R#，YYYY-MM-DD）——一句话结论

- **触发**：为什么做这件事（用户报了什么 / 什么数字不对）
- **发现**：查下来实际是什么，**带实测数字**
- **踩的坑**：下一个人会重犯的那些

### 规划变更
- [ ] 因此要改的排期 / 范围 / 已知欠账

### 下一步决定
- [ ] 待观察、待验证、暂时无解但要记着的
```

## 写什么才有价值

- **朝前看**：这一轮**改变了后面怎么走**的东西。
  「做完了 X」属于 `conclusion.md`，不属于这里。
- **数字带上采样条件**：`477ms` 要写清冷启动还是热跑，
  否则半年后没人判断得了它偏在哪一侧。
- **押注没押中就照实写差因，别改原来的数**——
  改掉等于把一次真实的推演失误抹成先见之明。
- **拿不准要不要记的，倾向记**。这份文件唯一的失败模式是空着。
